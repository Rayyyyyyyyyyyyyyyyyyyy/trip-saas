# Gemini integration ownership

Own the one V0 Gemini request/response adapter behind the provider-neutral `parseTrip` contract. Gemini types and metadata do not leave this boundary.

- `createGeminiTripParser` currently requires explicit model selection. Exact `gemini-3.8-flash` is the selected stable default candidate, not yet a production pin.
- `TripRuntimeApp` reads the primary candidate from `VITE_GEMINI_MODEL`. Local development may also provide `VITE_GEMINI_FALLBACK_MODEL`; it is offered only as a user-invoked retry after `provider_unavailable`, never as an automatic substitution. Exact-model benchmark runners do not read this fallback, and production remains unset until `complete-faithful-markdown-journey` records the required schema, deterministic, live and integrated acceptance evidence and explicitly activates the default. The predecessor hardening task 10.5 was transferred, not passed.
- After acceptance, the no-override production default is exact `gemini-3.8-flash`; never use a moving alias or silently fall back to another model. Every later default change reruns the same gates.
- The pre-provider input gate runs first: `validateUnifiedSourceDocument` re-checks schema, deterministic integrity, and agreement between `ParseTripRequest.sourceId` and the document, so an unvalidated or mispaired document never reaches an endpoint. It reports the single `source_document_invalid` code under the `source` diagnostic phase; the gate's internal rule is not surfaced, because naming it would leak schema paths or source content.
- Credentials travel only in the `x-goog-api-key` header. Provider envelopes, errors, model identity, and request metadata never enter ParsedTripDraft or CanonicalTrip.
- `interpretTrip` owns source validation, request-size/token preflight, local response schema, source coverage and Reviewable Draft gates. Gemini transport prepares provider-compatible requests, reports size estimates, retries `429` and `503` with bounded exponential backoff and honors abort signals; it does not own product validation rules or silently switch models.
- Each attempt runs under its own request deadline (`requestTimeoutMs`, default 120s) so a provider that accepts the connection and never answers still releases the intake surface's interaction lock, reported as `provider_timeout`.
- The application workflow already has locally verified stage/overall deadlines and an explicit stop action across reading, extraction, provider and local-validation stages. The provider attempt deadline is one additional bound; actual modal lifetime is application-owned.
- Failure codes stay phase-specific: `provider_unreachable` only for a lost connection, `provider_rejected` for a refused request (4xx), `provider_unavailable` for a provider-side fault (5xx), `authentication_failed` for a credential that was presented and refused, and `draft_not_reviewable` for the pre-Review gate rather than `invalid_response`.
